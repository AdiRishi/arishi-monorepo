[Kinds of tests](/adr/three-kinds-of-tests) explains the split. `workers/api/tests/e2e/` is the model for a Worker's E2E tests. `@repo/testing` holds the shared harness and stand-ins.

## Choose the kind

1. **Unit** when plain code, an Effect service, or a rendered component shows the behaviour.
2. **E2E** when it needs the Workers runtime: D1, R2, a queue batch, a cron run, a Durable Object, RPC between Workers, or a response from a Worker's routes.
3. **Integration** only for a happy path a person takes through the whole application. Failures and edge cases belong in the first two kinds.

## Every test

- Name the regression the test catches before writing it.
- Write expected values as literals, and assert whole values where you can.
- Build fixtures through the contract schemas, so a fixture the contract no longer accepts fails at once.
- Give cases with different outcomes separate tests. `it.each` is for cases that make the same assertion.

`it.effect`'s `TestClock` starts at zero. E2E tests use `it.live`, because the Worker under test runs on the real clock. Both give each test a `Scope`, so a test can `yield*` an RPC client without `Effect.scoped`.

## E2E tests

The tests reach a Worker only as Cloudflare and its neighbours do: `exports.default.fetch`, `.queue`, and `.scheduled`, and its RPC entrypoints through `clientOverBinding(group, { binding: exports.Name })`. A refactor inside the Worker leaves them untouched. Set state up through the Worker where it offers a way, and otherwise in storage.

- The test entry and the tests run in one isolate, so a stand-in keeps its state in module variables and tests import its helpers directly. Reset that state in the setup file.
- A stand-in for an RPC neighbour serves the contract's group with `rpcWebHandler`, so it can't drift from what the real Worker accepts.
- Work a handler starts with `waitUntil` can outlive its test. Wait for it to settle before the test ends, as the API's `upload` helper waits for its profile job.
- The web app's E2E project runs the build in `apps/web/dist/`. `pnpm test` builds it first; run `pnpm build` in `apps/web` before running that project on its own.

## Integration journeys

`infra/tests/integration/local-stack.test.ts` runs the stack with Alchemy and then the Playwright journeys beside it. It calls `Test.make` itself, because Alchemy's cleanup hook must run after `afterAll(destroy(Stack))`. A journey starts from an empty stack, so it creates what it needs.
